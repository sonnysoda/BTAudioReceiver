# 蓝牙音频接收器 — 需求规格（草案 v0.2）

> 状态：讨论中。`[待定]` 未决策，`[已确认]` 已拍板。
> 日期：2026-11-05 ｜ v0.2 变更：UI 改为 C++/WinRT + Rust Core；砍掉 booster 与开机自启

---

## 1. 定位

把 Windows 11 PC 变成蓝牙音箱：接收手机/平板推来的音频并播放。

与参考项目（sonnysoda/BluetoothAudioReceiver，MIT）的差异定位：
**应用内配对 + Win11 原生观感 + 更小的分发体积 + 结构化硬件诊断**。

---

## 2. 平台与技术约束 `[已确认]`

| 项 | 决策 |
|---|---|
| 目标平台 | 仅 Windows 11 |
| UI 层 | **C++/WinRT + WinUI 3**（官方 VS 工具链） |
| 业务层 | **Rust**，编译为 `cdylib`，经 C ABI 调用 |
| 核心 API | `Windows.Media.Audio.AudioPlaybackConnection`（WinRT） |
| 互操作 | `cbindgen` 生成头文件；Rust 导出少量 `extern "C"` + 事件回调 |
| 构建 | CMake + corrosion（GitHub `corrosion-rs/corrosion`，**非** crates.io 同名包） |

### 为什么不用纯 Rust

`windows-reactor`（官方 WinUI 3 for Rust）0.100.0 发布于 2026-09-03，
下载量 6.7k，注释仅 14 行 / 7.5 万行代码。API 可能变动、文档稀缺、无社区支持。
UI 层改用 C++/WinRT 可让这层风险归零，Rust 只承担其擅长的内核逻辑。

### 关键互操作风险

| 风险 | 应对 |
|---|---|
| CRT 混链（Rust `staticlib` 静态 CRT vs C++ `/MD`） | Rust 出 `cdylib`（DLL），完全隔离 CRT |
| 跨 FFI 调试困难 | Rust 侧结构化日志；边界函数逐个加 trace |
| 双工具链构建 | CMake `add_custom_command` 调 cargo；锁定 Rust/VS 版本 |

### 已知技术事实

- `AudioPlaybackConnection` 元数据为 `MarshalingType.Agile` + `ThreadingModel.Both`，
  可在任意线程调用，**不需要 STA 消息泵**。
- `StateChanged` 与 `DeviceWatcher` 回调线程不确定，需统一
  `channel → 回调 C++ → DispatcherQueue.TryEnqueue` 回 UI 线程。
- 微软文档明确：音频解码与输出由 **OS 蓝牙组件 + 系统音频端点**完成，
  App 只负责启用/建立连接。**App 全程不接触 PCM 数据。**

### 已明示并接受的代价

1. WinUI 3 自带渲染栈 + WASDK runtime，常驻内存远高于 Win32。
   **"省内存"不是本项目收益**；收益为 exe 体积小、冷启动快、无 GC。
2. 分发需自包含 WASDK runtime（+数十 MB）或要求预装运行时。
   单文件小 exe 不可行。

## 3. 功能需求

### P0 — 缺了就不成立

- [ ] A2DP Sink 连接 / 断开
- [ ] 已配对设备列表（连接状态 + 自动连接开关）
- [ ] 连接状态实时反馈（空闲 / 连接中 / 已连接 / 推流中 / 失败原因）
- [ ] 托盘常驻（图标随状态变化）
- [ ] 单实例（第二次启动唤起已有实例）
- [ ] 硬件兼容性自检：适配器是否支持 Sink 角色、驱动、蓝牙服务状态

### P1 — 决定好不好用

- [ ] 应用内配对（受总开关控制）
- [ ] 每设备自动连接（见 §4）
- [ ] 系统音量控制 0–100（见 §5）
- [ ] 音量合成器显示正确名称与图标（见 §5.3）
- [ ] 连接失败可读原因 + 一键诊断
- [ ] 滚动日志（上限 5MB，保留 1 份备份）

### P2 — 明确不做

- **音量 booster（100–500）** — 平台不支持，见 §5.2
- **开机自启** — 用户决定暂缓
- 多语言 / 自定义主题 / 自动更新 / 音频处理（EQ、可视化、录音）

## 4. 连接模型

### 4.1 自动连接语义 `[已确认]`

per-device 状态：开 → 检测到即自动连接；关 → 需手动。**新增设备默认开启。**

已知取舍：已配对设备（含家人手机、旧设备）默认会被自动接管。用户已确认接受。

### 4.2 Start 与 Open 的分工 `[已确认]`

| API | 语义 | 策略 |
|---|---|---|
| `Start()` | 允许远程设备推流（被动待命） | **对所有已配对设备永久常驻** |
| `Open()` | 本机主动拉取音频（主动接管） | 由 per-device 自动连接开关控制 |

关掉开关只等于"不抢"，不等于 App 失效——手机端主动选择 PC 仍然有声。

### 4.3 多设备冲突 `[已确认]`

- **最后出现者优先**
- **已有活跃连接时不抢占**
- **手动操作优先级永远高于自动连接**

### 4.4 断线重连 `[待定]`

重试 3 次 × 500ms（沿参考项目策略），仍失败则退回待命模式。

## 5. 音量与音频能力边界

### 5.1 音量控制 0–100 `[已确认]`

通过 `IAudioEndpointVolume::SetMasterVolumeLevelScalar(0.0–1.0)` 控制系统音量。
需处理默认设备切换（监听 `IMMNotificationClient` 重新绑定端点）。

### 5.2 Booster（100–500）不可行 `[已确认砍掉]`

原因（平台硬限制）：

- `SetMasterVolumeLevelScalar` 仅接受 **0.0–1.0**
- `SetMasterVolumeLevel` 的 dB 上限由 `GetVolumeRange()` 决定，上限 **0 dB**
- 系统音量链路在 API 层面 100% 封顶

理论可行的替代路径及其代价：

| 手段 | 可行性 | 代价 |
|---|---|---|
| APO（音频处理对象） | 技术可行 | 需驱动签名 + 管理员安装 + INF 注册 |
| WASAPI loopback 抓取 → 增益 → 虚拟声卡 | 唯一用户态路径 | 需虚拟声卡（或自带签名驱动）、延迟上升、架构重写 |
| 系统"响度均衡" | 仅能跳转设置页 | 非真增益，不可编程控制 |

补充：即使实现 500% 增益，无 limiter/软削波必然削波失真，听感劣化。
**结论：不做。** 用户反馈"声音小"应归因于手机端音量、A2DP 编码增益或扬声器功率。

### 5.3 音量合成器品牌化 `[新增]`

同类项目实测：A2DP 推流在 Windows 音量合成器中显示为 **"麦克风"**
（音频从手机"采入"，属 capture session）。
可用 `IAudioSessionManager2` 枚举会话（注意需同时查 capture 与 render 两侧）、
定位本进程会话并重命名为应用名 + 图标。

成本低、用户感知强，建议做。

### 5.4 其他蓝牙音频协议：不支持

| 协议 | 状态 |
|---|---|
| A2DP Sink（SBC/AAC） | ✅ 唯一可用路径 |
| LE Audio / LC3 / Auracast | ❌ Windows 仅支持 PC 作发送端，无接收端 API |
| aptX / LDAC / AAC 编解码协商 | ❌ 系统 + 芯片 + 手机三方协商，无公开 API |
| HFP 接收通话音频 | ❌ 无对应用户态 API |
| 自研协议栈 | ❌ 用户态仅开放 RFCOMM/GATT；A2DP 需裸 L2CAP，须写内核 profile 驱动（WDK + EV 证书 + attestation 签名） |

**协议层面锁死 A2DP Sink，这是 Windows 平台天花板。**

## 6. 配对策略 `[已确认]`

- 应用内置配对（`DeviceInformation.Pairing`）
- 总开关「由应用接管蓝牙配对」：开 → App 内配对；关 → 引导至系统设置，App 仅读已配对设备
- 总开关默认值 `[待定]`

---

## 7. 窗口与托盘行为 `[已确认]`

- 托盘常驻 + 独立主窗口（非弹出面板、不手绘标题栏）
- 主窗口使用 WinUI 3 标准标题栏，Mica 背景，跟随系统深浅色
- 关闭主窗口 → 最小化到托盘，不退出进程
- 托盘菜单：显示主窗口 / 连接状态 / 自动连接总控 / 退出
- 退出时释放所有 `AudioPlaybackConnection`，不留残留
